Clean Code 最小清单

第一性原理版 · 审计 Skill 脚本时照着打勾 · 判据是成本与风险，不是符合清单
根前提：代码是写给人看的（机器只认语法对不对，不在乎命名/长度/注释）。
由此只推出两根判据 —— A. 理解成本（让人一眼读懂意图与边界）· B. 修改风险（改动时不牵连出错）。
所有规则都是这两根的子树；检验不过的，就是噪音。
红 · 出现即脏，优先修 黄 · 有意的债，需注释+范围可控 绿 · 出现即干净

A. 理解成本 读起来费不费劲

B. 修改风险 改起来怕不怕

用法：审一段脚本，逐项打勾「我在这里发现了这个问题」。勾完看下方计数 ——
红（必须修）：0 · 黄（可控债）：0 · 绿（已达标）：0
判据不是清单：红了就修；黄了只要「注释说清 + 范围可控」就暂时可接受；绿的出现说明干净。 同一处若「为了清单而清单」（为短拆成七层 tiny function、为 DRY 抽象没人用的接口），反而是脏的。
